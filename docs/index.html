FileWatch

Ransomware muda seus arquivos de um jeito que dá para medir.

Um projeto de estudo em Java 17 + Spring Boot que observa uma única pasta, recalcula hash e entropia só do arquivo que mudou e decide, numa janela de 10 segundos, se o padrão das mudanças tem cara de ataque. Acompanha um simulador benigno para você provocar o alerta na sua própria máquina, sem risco.

Pesquisa e estudo de 2026. Técnicas de ransomware, defesas, referências e versões (Java 17, Spring Boot 3.5) refletem esse ano; se estiver lendo bem depois, confira o que mudou.

Projeto de portfólio. Não é antivírus, não tem driver de kernel e não substitui um EDR nem backup. A defesa que de fato recupera seus dados continua sendo backup offline e versionado.

Por que existe

Assinaturas chegam tarde. Comportamento, não.

Um antivírus tradicional reconhece malware por assinatura: um hash ou um padrão de bytes já catalogado. Isso funciona para o que já foi visto. Uma variante nova de ransomware, recompilada ou ofuscada, passa sem assinatura nenhuma.

Só que todo ransomware de criptografia precisa fazer a mesma coisa para cumprir o objetivo: abrir muitos arquivos do usuário, trocar o conteúdo por dados cifrados, em geral renomear e deixar uma nota pedindo pagamento. No catálogo MITRE ATT&CK isso é a técnica T1486, Data Encrypted for Impact. Esse comportamento deixa rastros mensuráveis, qualquer que seja o código:

  • Volume: dezenas de arquivos alterados em segundos, coisa que uma pessoa editando documentos não faz.
  • Aleatoriedade: dado cifrado é indistinguível de ruído. A entropia do arquivo salta para perto de 8 bits por byte.
  • Nomes: extensões como .locked e .encrypted e arquivos como README_DECRYPT.txt.

O FileWatch mede exatamente esses três rastros. É a mesma ideia de ferramentas acadêmicas como CryptoLock, UNVEIL e ShieldFS (referências no fim), em versão pequena o bastante para ler o código inteiro numa tarde.

O objetivo é didático: praticar I/O de arquivos, hashing por streaming, entropia, eventos e processamento assíncrono no Spring, com uma narrativa de segurança que dá para demonstrar ao vivo.

Como funciona

Quatro peças que só conversam por eventos

Cada peça publica um evento no ApplicationEventPublisher do Spring e não sabe quem vai consumir. Isso deixa cada uma testável sozinha e permite trocar o alerta (log hoje, dashboard amanhã) sem tocar no detector.

  1. FolderWatcher registra a pasta e todas as subpastas (o WatchService do Java não é recursivo). Junta rajadas de eventos do mesmo arquivo por 300 ms e publica um FileChangedEvent.
  2. FileAnalyzer roda num pool de threads próprio. Lê o arquivo uma vez em blocos de 64 KB: o mesmo laço alimenta o SHA-256 e a contagem de bytes da entropia. Se o hash não mudou, para ali. Se mudou, publica FileAnalyzedEvent com a entropia nova e a anterior.
  3. RansomwareDetector guarda os eventos dos últimos 10 segundos e avalia os quatro sinais a cada evento novo.
  4. AlertListener loga o alerta e grava uma linha JSON em alerts.log. Não toca em arquivo nenhum: mexer nos dados do usuário sem confirmação está fora do escopo.

Por que assíncrono: se a thread que ouve o sistema de arquivos parasse para hashear um arquivo de 2 GB, os eventos seguintes se acumulariam e o sistema operacional descartaria parte deles (OVERFLOW). Quando a fila do pool enche, a política CallerRunsPolicy faz a thread de debounce esperar, o que aplica backpressure em vez de perder eventos.

O sinal mais forte

Entropia de Shannon: quão imprevisível é cada byte

Conte quantas vezes cada um dos 256 valores de byte aparece no arquivo e transforme em probabilidades. A entropia diz quantos bits de informação, em média, cada byte carrega:

H = − Σ p(x) · log₂ p(x) para x = 0 … 255 → 0 ≤ H ≤ 8 bits/byte

Um arquivo só com a letra a tem H = 0: nenhuma surpresa. Texto em português fica perto de 4,5 porque poucas letras dominam. Dado cifrado usa todos os 256 valores quase por igual e chega a 7,99. O FileWatch calcula H sobre os primeiros 256 KB de cada arquivo, o que basta para distinguir e mantém o custo baixo em arquivos grandes.

Histograma: um traço por valor de byte (0 a 255), altura proporcional à frequência. Texto concentra tudo na faixa ASCII; bytes aleatórios espalham uma camada uniforme por todo o eixo.

Tipo de conteúdoEntropia típicaO que isso significa para o detector
Arquivo de zeros, logs repetitivos0 – 2Muito previsível.
Texto, código-fonte, CSV, JSON4 – 5,5O caso típico de documento editável.
Executáveis, PDFs sem compressão5 – 6,5Estruturas variadas, mas longe do máximo.
ZIP, JPEG, MP4, DOCX (é um zip)7,5 – 7,99Já comprimidos. Alta entropia sozinha não prova nada.
Dados cifrados (AES, ChaCha20)≈ 7,99Indistinguível de aleatório.

Por isso o sinal S2 exige duas condições ao mesmo tempo: entropia nova ≥ 7,5 e subida de pelo menos 2,0 em relação ao baseline. Um JPEG que continua JPEG não dispara, e um relatório .txt que virou ruído dispara.

Memória do monitor

Baseline: saber como cada arquivo era antes

O que fica guardado

Para cada arquivo: caminho, tamanho, data de modificação, SHA-256 e entropia. Tudo em baseline.json, fora do sandbox, salvo de forma atômica: escreve num temporário e faz move. Se o arquivo estiver corrompido, o monitor começa vazio e registra o erro, sem cair.

Varredura incremental

No start, arquivo com mesmo tamanho e mesma data do baseline é cache hit e não é re-hasheado. O log mostra Varredura inicial: 43 arquivos, 43 cache hits…. Só o que mudou com o monitor desligado é lido de novo.

A primeira execução não alerta

Sem baseline no disco, todo arquivo seria “novo” e o S1 dispararia na hora. Então a primeira varredura só constrói o baseline, sem alimentar o detector.

Por que SHA-256

A data de modificação muda sem o conteúdo mudar (um touch, um antivírus, uma sincronização). O hash confirma se os bytes mudaram de fato. Isso também vira a base para uma consulta de reputação de hash no futuro.

A decisão

Quatro sinais numa janela de 10 segundos

S1 · mass-modification-threshold = 30

Modificação em massa

30 ou mais arquivos distintos com conteúdo alterado na janela. Criação e remoção também contam.

S2 · entropy-spike-count = 10

Salto de entropia

10 ou mais arquivos que foram para ≥ 7,5 bits/byte subindo pelo menos 2,0.

S3 · suspicious-extensions

Extensão suspeita

Qualquer arquivo criado ou renomeado para .locked, .encrypted, .crypt ou .enc.

S4 · ransom-note-patterns

Nota de resgate

Nomes que casam com readme.*decrypt, how.*to.*decrypt ou restore.*files.

Um sinal sozinho gera WARNING. Dois ou mais sinais diferentes geram HIGH. Depois de um HIGH, os alertas ficam silenciados por 30 segundos, e um WARNING igual ao anterior também, senão cada evento dentro da janela repetiria o mesmo aviso. A combinação é o que reduz falso positivo: copiar 60 fotos dispara S1, mas não S2 (não havia entropia anterior para subir).

      Detalhes que custam caro
      
Armadilhas do WatchService

      

        

          
ProblemaComo o FileWatch lida

          
            
Não é recursivo: só avisa sobre a pasta registrada.Registra a árvore inteira no start e cada subpasta nova assim que ela aparece.

            
Uma gravação gera vários ENTRY_MODIFY seguidos.Debounce de 300 ms por arquivo: só o último evento da rajada segue adiante.

            
OVERFLOW: o SO descartou eventos porque a fila encheu.Re-varre o diretório afetado. Remoções perdidas nesse caso só são reconciliadas no próximo start.

            
Renomear chega como DELETE + CREATE.O arquivo renomeado não herda a entropia anterior. Por isso o S2 depende de ver a sobrescrita antes da renomeação.

            
No Windows, o arquivo pode estar travado por quem está escrevendo.A leitura falha em silêncio (nível DEBUG) e o próximo MODIFY tenta de novo.

            
Symlinks e junctions podem apontar para fora.A varredura não segue links e todo caminho passa pelo PathGuard, que compara o caminho canônico.

          
        

      

    


    

      Segurança do laboratório
      
Seguro de rodar na sua máquina, por construção

      

        
Um projeto que simula ransomware precisa provar que não é ransomware. As garantias abaixo estão no código e a maioria tem teste automatizado: o laboratório só toca na pasta do projeto. Mesmo assim, a recomendação para qualquer teste com simulação de malware é usar um ambiente controlado.

      Ambiente controlado
      
Seguro na sua máquina, melhor ainda isolado

      

        
As proteções do código confinam tudo a ./sandbox. Um ambiente isolado acrescenta uma garantia que não depende do código: se algo der errado, você descarta o ambiente e pronto. Também é o lugar certo para calibrar limiares sem medo.

      

      

        
VM com snapshot
VirtualBox, Hyper-V, VMware ou UTM. Instale Java 17 e Maven, clone o repositório e tire um snapshot. Rode lab demo, ajuste o que quiser e restaure o snapshot no fim. É o isolamento mais completo.

        
Windows Sandbox
VM descartável nativa do Windows Pro e Enterprise. Tudo que acontece lá dentro some quando você fecha a janela.

        
Contêiner Docker
Uma imagem eclipse-temurin:17 com Maven, clonando o repositório dentro do contêiner. Rápido e descartável no Linux e no macOS.

        
Pasta do projeto
O teste básico. Sem VM, as camadas da seção anterior garantem que monitor e simulador só tocam em ./sandbox, baseline.json e alerts.log.

      Limitações
      
O que este projeto não resolve

      

        
É reativo
Em espaço de usuário, o alerta sai durante ou depois do início do dano. É detecção precoce, não prevenção. Bloquear exigiria um minifiltro de kernel, como fazem os EDRs.

        
Evasão por lentidão
Um ataque que cifra um arquivo a cada 15 segundos nunca enche a janela de 10 s. Veja o cenário “Ransomware lento” na bancada do detector.

        
Falsos positivos
Copiar muitas fotos ou compactar em lote dispara S1. Só vira HIGH com um segundo sinal, mas uma whitelist de processos ou pastas ajudaria.

        
Eventos perdidos
Sem hook de kernel, um OVERFLOW pode esconder remoções até o próximo start.

Glossário

      

        
Baseline
Fotografia do estado conhecido de cada arquivo, usada como referência para decidir se algo mudou.

        
Debounce
Esperar um intervalo sem novos eventos antes de agir, para tratar uma rajada como um evento só.

        
Backpressure
Fazer o produtor desacelerar quando o consumidor não dá conta, em vez de descartar trabalho.

        
Entropia
Medida de imprevisibilidade de uma sequência de símbolos, em bits por símbolo.

        
Janela deslizante
Conjunto dos eventos mais recentes dentro de um intervalo fixo que anda junto com o relógio.

        
Cooldown
Período em que alertas repetidos são silenciados depois de um alerta.

        
Path traversal
Uso de .. ou de links para escapar de uma pasta permitida (CWE-22, CWE-59).

        
Junction
Tipo de link de diretório do NTFS. O Java não o reporta como symlink, por isso a comparação por caminho canônico.

        
EDR
Endpoint Detection and Response: ferramenta que monitora processos e arquivos no nível do SO e pode bloquear ações.

        
Backup 3-2-1
Três cópias, em dois tipos de mídia, uma fora do local (e de preferência offline ou imutável).
